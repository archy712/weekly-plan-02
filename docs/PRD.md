# 부서별 주간업무일지 관리 웹 애플리케이션 MVP PRD

## 🎯 핵심 정보

**목적**: 부서원들이 한 곳에서 주간 업무 진행 상황을 기록·추적하고, 관리자는 모든 부서의 업무 현황을 한눈에 파악할 수 있게 한다.
**사용자**: 여러 부서로 구성된 조직의 실무자(부서 소속 일반 사용자)와 전체 부서 현황을 관리하는 관리자.
**범위**: 이 문서는 MVP(구현 완료, `docs/roadmap/ROADMAP_mvp.md` Task 001~024)와 v1 고도화(`docs/roadmap/ROADMAP_v1.md` Task 025~037)를 모두 포함한다. v1 중 관리자 콘솔(F019·F020)·기간 범위 검색(F021)·통계 대시보드(F024)는 구현 완료, 댓글·멘션(F022)·실시간 알림(F023)은 계획 단계다. v1 범위의 기능·페이지에는 **"(v1)"** 표기를 병기한다.

## 🚶 사용자 여정

```
1. 랜딩 페이지
   ├─ [로그인] 버튼 클릭 ──────────────┐
   └─ [회원가입] 버튼 클릭 ─────┐       │
                              ↓       ↓
                     2. 회원가입 페이지   2. 로그인 페이지
                     - 이메일/비밀번호     - 이메일/비밀번호 로그인
                       입력 후 가입         또는 [구글로 계속하기]
                     ↓ 가입 성공(이메일 확인 없이 즉시 로그인됨)
                     가입 완료 안내 표시(1.5초)   ↓ 로그인 성공
                     → 랜딩 페이지로 자동 이동 ────┘
                     (로그인 상태의 랜딩은 [주간업무일지 보러가기] 버튼 노출)
                              ↓
              3. 인증 상태 자동 확인 (부서 설정 여부 체크)

     [부서 미설정] → 4. 프로필 페이지(온보딩)         [부서 설정됨]
                     - 부서 선택 후 저장 ───────────────────┐
                     (저장 전까지 다른 페이지 접근 차단)       ↓
                                                  5. 주간업무일지 목록 페이지
                                                     (검색·부서 필터·페이지네이션, 모든 로그인 사용자가
                                                      전체 부서 조회 가능 — 기본값만 일반 유저는 자기 부서)
                     ↓ [신규 작성]        ↓ 항목 클릭         ↓ [PDF 다운로드]
              6. 작성 페이지         7. 상세 페이지          PDF 파일 다운로드
                 - 입력 후 저장        - 조회/수정/진행상태변경/삭제  (목록 페이지 유지)
                     ↓ 저장 성공          ↓ 완료
                     └──────── 5. 주간업무일지 목록 페이지로 복귀 ────────┘
```

- 부서 미설정 상태에서는 `주간업무일지 목록/작성/상세` 등 모든 보호된 페이지 접근이 자동으로 **프로필 페이지**로 리디렉션된다.
- 이메일/비밀번호 찾기 등 기존 스타터킷의 인증 보조 흐름(비밀번호 재설정 등)은 본 PRD 범위에서 변경하지 않고 그대로 유지한다.
- 회원가입은 이메일 인증(Confirm Email) 없이 가입과 동시에 로그인 처리된다(Supabase Auth 설정).
- 주간업무일지 **조회(SELECT)는 로그인한 모든 사용자에게 부서 무관하게 공개**되고, **쓰기(작성/수정/삭제/진행상태변경)만 작성자의 소속 부서 또는 관리자로 제한**된다. 상세 페이지는 서버에서 계산한 쓰기 권한(`canWrite`)에 따라 수정/삭제/진행상태 선택 UI 노출 여부를 결정한다.
- **(v1)** 관리자 계정은 공통 헤더의 "관리자 콘솔" 링크(관리자에게만 노출되는 유일한 진입점)를 통해 대시보드·부서 관리·사용자 관리 3개 탭으로 이동한다. 관리자가 아닌 계정은 URL을 직접 입력해도 주간업무일지 목록 페이지로 리디렉션된다.
- **(v1)** 상세 페이지에서 댓글을 작성하며 `@`로 다른 사용자를 멘션할 수 있다(부서 무관하게 모든 로그인 사용자가 작성 가능). 자신이 멘션되거나 자신이 쓴 글에 댓글이 달리면 새로고침 없이 공통 헤더의 알림 벨에 즉시 표시되고, 클릭 시 해당 댓글 위치로 이동하며 읽음 처리된다.
- **(v1)** 관리자 콘솔의 대시보드 탭(관리자 전용, 관리자 콘솔 진입 시 기본 랜딩 화면)에서 부서별·기간별·상태별 업무 현황을 요약 카드와 차트로 확인할 수 있다.

### 3. v1 고도화 기능 (계획)

> MVP에서 "MVP 이후 기능"으로 제외했던 6가지를 정식 기능으로 명세한다. 상세 구현 계획(Phase·Task 단위)은 `docs/roadmap/ROADMAP_v1.md`를 참고. 관리자 콘솔(F019·F020)은 기존 `profiles`/`departments`의 RLS를 확장하는 유일한 작업군이라 다른 v1 기능보다 먼저 진행한다.

| ID | 기능명 | 설명 | 도입 이유 | 관련 페이지 |
|----|--------|------|----------|------------|
| **[F019]** | 부서 관리 UI (v1) | 관리자가 부서를 추가·이름 수정·비활성화(소프트 삭제)할 수 있는 화면. 소속 부서원 또는 주간업무일지가 있는 부서는 하드 삭제가 자동으로 차단되고, 비활성화된 부서는 신규 선택 목록에서만 제외되며 과거 데이터 조회에는 계속 노출된다 | 부서가 초기 seed 데이터로 고정되어 있어 조직 개편(신설/이름 변경)을 반영할 수 없었던 한계 해소 | 관리자 콘솔 - 부서 관리 페이지 |
| **[F020]** | 사용자 관리 UI (v1) | 관리자가 전체 사용자 목록을 검색·필터로 조회하고, 개별 사용자의 상세 화면(프로필 전체 정보 + 작성한 주간업무일지 요약)을 확인하며, 목록과 상세 양쪽에서 역할(`user`/`admin`)과 소속 부서를 지정/변경. 본인 역할 변경과 마지막 관리자의 자기 강등은 UI·DB 양쪽에서 차단 | Supabase 콘솔에서 SQL로 직접 변경해야 했던 관리자 지정 절차를 UI로 대체 | 관리자 콘솔 - 사용자 관리 목록/상세 페이지 |
| **[F021]** | 기간 범위 검색/필터 (v1) | 시작일/목표종료일 범위(기간이 겹치는 항목 기준)로 목록을 좁히는 필터. "이번 주/이번 달/최근 3개월" 프리셋을 제공하며 기존 부서·상태·키워드 필터와 조합 가능. PDF 다운로드 결과도 적용된 기간 필터와 항상 일치 | 목록이 누적될수록 특정 기간의 업무만 좁혀보는 탐색 요구가 커짐(키워드 검색 F016으로는 기간 조건을 표현할 수 없음) | 주간업무일지 목록 페이지 |
| **[F022]** | 댓글·멘션 협업 (v1) | 주간업무일지 상세 페이지에 plain text 댓글을 작성(1단계 대댓글 지원, 소프트 삭제)하고 `@`로 다른 사용자를 멘션. 댓글 작성은 부서 제한 없이 모든 로그인 사용자에게 허용되고(F007의 전 부서 공개 조회와 일관성 유지), 수정·삭제는 작성자 본인 또는 관리자로 제한 | 부서 간 업무 공유(F007)에서 한 걸음 나아가 실제 의견 교환·협업이 가능하도록 함 | 주간업무일지 상세 페이지 |
| **[F023]** | 실시간 알림 (v1) | 자신이 멘션되거나 자신이 쓴 글에 댓글·답글이 달리면 새로고침 없이 공통 헤더의 알림 벨에 즉시 표시(Supabase Realtime). 클릭 시 해당 댓글 위치로 이동해 읽음 처리되며, 실시간 연결이 끊겨도 앱 사용에는 지장이 없다 | 협업 기능(F022)이 실제로 쓰이려면 알림 없이는 새 댓글·멘션이 발견되지 않음 | 공통 헤더(전 페이지) |
| **[F024]** | 통계/대시보드 차트 (v1) | 부서별·기간별·상태별 업무 현황을 요약 카드 4종과 차트 4종(부서별 건수, 진행상태 분포, 월별 생성·완료 추이, 부서별 예상 M/M·금액)으로 시각화. 기간·부서 필터를 자체적으로 제공 | 목록 형태로는 파악하기 어려운 조직 전체의 업무 현황을 관리자가 한눈에 확인하려는 요구(구현 중 전 사용자 공개 → **관리자 전용**으로 전환, 아래 페이지별 상세 참고) | 관리자 콘솔 - 대시보드 페이지 |

### 4. v1 이후에도 제외되는 기능

- 부서 계층 구조(상위/하위 부서), 부서장 지정, 부서 통폐합(로그 일괄 이관)
- 사용자 계정 삭제/비활성화, 초대 기반 가입, `user`/`admin` 2단계를 넘어서는 역할 체계
- 저장된 필터 프리셋(사용자별 즐겨찾기), 상대 기간 표현(`지난 분기` 등)의 동적 계산
- 댓글 첨부파일, 이모지 반응, 댓글 검색·페이지네이션, 2단계 이상 대댓글
- 이메일 알림, 브라우저 푸시 알림(Web Push), 알림 유형별 on/off 설정 화면, 실시간 댓글 스트리밍
- 차트 이미지 내보내기(PNG), 대시보드 PDF 리포트, 사용자별 대시보드 커스터마이징(위젯 배치)

> **(v1)** `profiles.role`은 관리자 콘솔(F020)에서 UI로 변경 가능하다. 단 `profiles`의 `UPDATE` 정책(`profiles_update_own_or_admin`)이 행 단위 제한만 하므로, `role` 값이 바뀌는 UPDATE는 호출자가 `is_admin()`이 아니면 예외를 발생시키는 `BEFORE UPDATE` 트리거로 별도 차단한다(일반 사용자의 자기 역할 상승 방지). 마지막 남은 관리자의 자기 강등도 동일한 트리거에서 거부한다.

> `content`는 저장 시점과 렌더링 시점 양쪽에서 DOMPurify로 sanitize해 허용된 태그(`p, br, strong, em, u, h1~h3, ul, ol, li, a, blockquote`)만 남긴다(XSS 방어).

### weekly_log_attachments (첨부파일)

| 필드 | 설명 | 타입/관계 |
|------|------|----------|
| id | 고유 식별자 | UUID |
| weekly_log_id | 소속 주간업무일지 | → weekly_logs.id (on delete cascade) |
| department_id | 소속 부서(작성 시점 기준 비정규화) | → departments.id |
| file_name | 원본 파일명 | text |
| file_path | 스토리지 객체 경로(`{department_id}/{weekly_log_id}/{uuid}-{파일명}`) | text, unique |
| file_size | 파일 크기(바이트) | integer, `0 < size <= 5242880`(5MB) CHECK 제약 |
| content_type | MIME 타입 | text, nullable |
| uploaded_by | 업로드한 사용자 | → profiles.id |
| created_at | 업로드일시 | timestamp |

> 실제 파일 바이너리는 `weekly-log-attachments`라는 private Supabase Storage 버킷(`file_size_limit` 5MB)에 저장되고, 이 테이블은 메타데이터만 관리한다.
> RLS는 `weekly_logs`와 동일하게 SELECT 전 부서 공개, INSERT/DELETE는 업로더의 소속 부서 또는 `admin`으로 제한한다(수정은 지원하지 않음 — 삭제 후 재업로드).
> 스토리지 버킷 자체의 RLS도 객체 경로의 최상위 폴더(`department_id`)가 요청자 소속 부서와 일치해야 읽기/쓰기가 가능하도록 구성한다.
> 파일 크기 5MB 제한은 (1) 클라이언트 선택 즉시 거부, (2) 스토리지 버킷 `file_size_limit`, (3) 이 테이블의 CHECK 제약, 3중으로 강제한다.

| deleted_at | 소프트 삭제 일시 | timestamp, nullable |
| created_at / updated_at | 작성/수정일시 | timestamp |

> RLS는 SELECT 전 인증 사용자 공개(`weekly_logs`가 이미 전 부서 공개이므로 댓글만 부서로 막지 않음), INSERT는 **부서 무관하게 작성자 본인**이면 허용(`weekly_logs`의 부서 제한을 그대로 복사하면 "타 부서 업무에 의견 남기기"가 불가능해져 기능이 무의미해지므로, 이 지점만 기존 부서 기반 권한 모델과 의도적으로 다르게 설계), UPDATE/DELETE는 작성자 본인 또는 `admin`으로 제한한다. 대댓글이 있는 댓글은 물리 삭제 대신 `deleted_at`을 채운다.
> 댓글은 Tiptap 리치 텍스트가 아니라 plain text로 저장·렌더링하며, 저장 시 서버에서 1~2000자·공백만 입력을 거부한다.

### weekly_log_comment_mentions (댓글 멘션, v1)

| 필드 | 설명 | 타입/관계 |
|------|------|----------|
| comment_id | 댓글 | → weekly_log_comments.id (on delete cascade) |
| mentioned_user_id | 멘션된 사용자 | → profiles.id |
| created_at | 생성일시 | timestamp |

> `unique(comment_id, mentioned_user_id)`. 멘션은 본문 텍스트 파싱이 아니라 별도 행으로 정규화해, 알림 생성(F023)이 텍스트 파싱 없이 "누구에게 알릴지"를 결정할 수 있게 한다. 클라이언트가 보낸 멘션 목록은 신뢰하지 않고, 서버 액션이 본문의 멘션 토큰을 파싱해 실존하는 `profiles.id`만 삽입한다. SELECT는 전체 공개, INSERT는 해당 댓글의 작성자만 가능하다.

### notifications (알림, v1)

| 필드 | 설명 | 타입/관계 |
|------|------|----------|
| id | 고유 식별자 | UUID |
| recipient_id | 수신자 | → profiles.id (on delete cascade) |
| actor_id | 알림을 발생시킨 사용자 | → profiles.id |
| type | 알림 유형 | text (`mention` \| `comment` \| `reply` CHECK 제약) |
| weekly_log_id | 관련 주간업무일지 | → weekly_logs.id (on delete cascade) |
| comment_id | 관련 댓글 | → weekly_log_comments.id (on delete cascade), nullable |
| read_at | 읽음 처리 일시 | timestamp, nullable |
| created_at | 생성일시 | timestamp |

> 알림은 부서 기반이 아니라 **수신자 개인 기준**으로 RLS를 적용하는 유일한 테이블이다: SELECT는 `recipient_id = auth.uid()`만, UPDATE는 수신자 본인이 `read_at`만 변경 가능(다른 컬럼 변경은 트리거로 차단, `profiles.role` 보호와 동일한 패턴), DELETE는 수신자 본인만. **INSERT는 클라이언트에 허용하지 않고** `weekly_log_comments`/`weekly_log_comment_mentions`에 새 행이 생길 때 동작하는 `SECURITY DEFINER` 트리거로만 생성한다(자기 자신에게는 알림을 만들지 않음). Supabase Realtime publication에 이 테이블만 등록해 헤더 알림 벨(F023)에 실시간으로 반영한다.
