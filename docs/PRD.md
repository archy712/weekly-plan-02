# 부서별 주간업무일지 관리 웹 애플리케이션 MVP PRD

## 🎯 핵심 정보

**목적**: 부서원들이 한 곳에서 주간 업무 진행 상황을 기록·추적하고, 관리자는 모든 부서의 업무 현황을 한눈에 파악할 수 있게 한다.
**사용자**: 여러 부서로 구성된 조직의 실무자(부서 소속 일반 사용자)와 전체 부서 현황을 관리하는 관리자.

## 🚶 사용자 여정

```
1. 랜딩 페이지
   ├─ [로그인] 버튼 클릭 ──────────────┐
   └─ [회원가입] 버튼 클릭 ─────┐       │
                              ↓       ↓
                     2. 회원가입 페이지   2. 로그인 페이지
                     - 이메일/비밀번호     - 이메일/비밀번호 로그인
                       입력 후 가입         또는 [구글로 계속하기]
                     ↓ 가입 성공(이메일 확인 없이 즉시 로그인됨)
                     가입 완료 안내 표시(1.5초)   ↓ 로그인 성공
                     → 랜딩 페이지로 자동 이동 ────┘
                     (로그인 상태의 랜딩은 [주간업무일지 보러가기] 버튼 노출)
                              ↓
              3. 인증 상태 자동 확인 (부서 설정 여부 체크)

     [부서 미설정] → 4. 프로필 페이지(온보딩)         [부서 설정됨]
                     - 부서 선택 후 저장 ───────────────────┐
                     (저장 전까지 다른 페이지 접근 차단)       ↓
                                                  5. 주간업무일지 목록 페이지
                                                     (검색·부서 필터·페이지네이션, 모든 로그인 사용자가
                                                      전체 부서 조회 가능 — 기본값만 일반 유저는 자기 부서)
                     ↓ [신규 작성]        ↓ 항목 클릭         ↓ [PDF 다운로드]
              6. 작성 페이지         7. 상세 페이지          PDF 파일 다운로드
                 - 입력 후 저장        - 조회/수정/진행상태변경/삭제  (목록 페이지 유지)
                     ↓ 저장 성공          ↓ 완료
                     └──────── 5. 주간업무일지 목록 페이지로 복귀 ────────┘
```

- 부서 미설정 상태에서는 `주간업무일지 목록/작성/상세` 등 모든 보호된 페이지 접근이 자동으로 **프로필 페이지**로 리디렉션된다.
- 이메일/비밀번호 찾기 등 기존 스타터킷의 인증 보조 흐름(비밀번호 재설정 등)은 본 PRD 범위에서 변경하지 않고 그대로 유지한다.
- 회원가입은 이메일 인증(Confirm Email) 없이 가입과 동시에 로그인 처리된다(Supabase Auth 설정).
- 주간업무일지 **조회(SELECT)는 로그인한 모든 사용자에게 부서 무관하게 공개**되고, **쓰기(작성/수정/삭제/진행상태변경)만 작성자의 소속 부서 또는 관리자로 제한**된다. 상세 페이지는 서버에서 계산한 쓰기 권한(`canWrite`)에 따라 수정/삭제/진행상태 선택 UI 노출 여부를 결정한다.

### 2. MVP 필수 지원 기능

| ID | 기능명 | 설명 | MVP 필수 이유 | 관련 페이지 |
|----|--------|------|-------------|------------|
| **[F010]** | 기본 인증 | 이메일/비밀번호 회원가입, 로그인, 로그아웃 | 서비스 이용을 위한 최소 인증 | 로그인 페이지, 회원가입 페이지 |

| **[F013]** | 다크모드 토글 | 라이트/다크 테마를 전환 | 요청된 필수 UI 요구사항 | 전체 페이지(공통 헤더) |

| **[F015]** | 랜딩 기능 소개 카드 | 주요 기능을 카드 형식으로 소개 | 요청된 필수 랜딩 페이지 요구사항 | 랜딩 페이지 |

### 3. MVP 이후 기능 (제외)

- 부서 관리(부서 추가/수정/삭제) UI — 부서는 초기 데이터로만 관리
- 관리자 역할 지정/변경 UI — role 컬럼은 DB에서 수동 관리
- 주간업무일지 기간 범위 검색/필터(키워드 검색은 F016으로 구현됨)
- 댓글, 멘션 등 협업 기능
- 실시간 알림 시스템
- 통계/대시보드 차트

## 📱 메뉴 구조

```
📱 부서별 주간업무일지 관리 내비게이션

🌐 공통 헤더 (비로그인 시)
├── 🏠 홈(랜딩)
│   └── 기능: F015 (주요 기능 카드 소개)
├── 🔑 로그인
│   └── 기능: F010, F011 (이메일/구글 로그인)
├── ✍️ 회원가입
│   └── 기능: F010 (이메일 회원가입)
└── 🌓 다크모드 토글
    └── 기능: F013

👤 로그인 사용자 메뉴 (부서 설정 완료 시, 일반/관리자 공통)
└── 📋 주간업무일지 목록 (검색 + 부서 필터 + 페이지네이션)
    └── 기능: F001, F007, F016 (전체 부서 조회, 신규작성/상세 진입점)

🔧 공통 메뉴 (모든 로그인 사용자)
├── 👤 프로필
│   └── 기능: F012 (부서 선택/변경), F018 (전화번호·아바타·자기소개)
├── 🌓 다크모드 토글
│   └── 기능: F013
└── 🚪 로그아웃
```

일반 사용자와 관리자는 완전히 동일한 **주간업무일지 목록 페이지**를 사용한다. 부서 필터·검색·페이지네이션은 `role`과 무관하게 모두에게 노출되며, `role`에 따른 차이는 **부서 필터의 기본 선택값**(일반 사용자는 자기 부서, 관리자는 전체)과 **쓰기 권한**(작성/수정/삭제/진행상태변경은 자기 부서 또는 관리자로 제한)뿐이다.

> **구현 기능:** `F010`, `F018`, `F013`, `F014` | **인증:** 비로그인 전용

| 항목 | 내용 |

| 필드 | 설명 | 타입/관계 |
|------|------|----------|
| id | 고유 식별자 | UUID |
| department_id | 소속 부서 | → departments.id |
| author_id | 작성자 | → profiles.id |
| title | 업무명(제목) | text |
| content | 업무 상세 내용(본문) | text (리치 텍스트 에디터가 생성한 sanitize된 HTML 문자열) |
| start_date | 시작일 | date |
| target_end_date | 목표 종료일 | date |
| status | 진행상태 | text (`planned` \| `in_progress` \| `completed`, 기본값 `in_progress`) |
| estimated_mm | 예상 소요 M/M | numeric, nullable (선택 입력) |
| estimated_cost | 예상 소요 금액 | integer, nullable (선택 입력) |
| partner_company | 관련 협력 회사 | text, nullable (선택 입력) |
| created_at | 작성일시 | timestamp |
| updated_at | 수정일시 | timestamp |

> `departments`는 초기 데이터(seed)로만 관리하고 별도 관리 UI는 MVP 범위에서 제외한다. `profiles.role`은 Supabase에서 수동으로 `admin`으로 변경한다(관리자 지정 UI 없음).
> `weekly_logs`의 RLS는 SELECT를 전 부서에 공개하고, INSERT/UPDATE/DELETE만 작성자의 소속 부서 또는 `admin`으로 제한한다.
> `content`는 저장 시점과 렌더링 시점 양쪽에서 DOMPurify로 sanitize해 허용된 태그(`p, br, strong, em, u, h1~h3, ul, ol, li, a, blockquote`)만 남긴다(XSS 방어).

### weekly_log_attachments (첨부파일)

| 필드 | 설명 | 타입/관계 |
|------|------|----------|
| id | 고유 식별자 | UUID |
| weekly_log_id | 소속 주간업무일지 | → weekly_logs.id (on delete cascade) |
| department_id | 소속 부서(작성 시점 기준 비정규화) | → departments.id |
| file_name | 원본 파일명 | text |
| file_path | 스토리지 객체 경로(`{department_id}/{weekly_log_id}/{uuid}-{파일명}`) | text, unique |
| file_size | 파일 크기(바이트) | integer, `0 < size <= 5242880`(5MB) CHECK 제약 |
| content_type | MIME 타입 | text, nullable |
| uploaded_by | 업로드한 사용자 | → profiles.id |
| created_at | 업로드일시 | timestamp |

> 실제 파일 바이너리는 `weekly-log-attachments`라는 private Supabase Storage 버킷(`file_size_limit` 5MB)에 저장되고, 이 테이블은 메타데이터만 관리한다.
> RLS는 `weekly_logs`와 동일하게 SELECT 전 부서 공개, INSERT/DELETE는 업로더의 소속 부서 또는 `admin`으로 제한한다(수정은 지원하지 않음 — 삭제 후 재업로드).
> 스토리지 버킷 자체의 RLS도 객체 경로의 최상위 폴더(`department_id`)가 요청자 소속 부서와 일치해야 읽기/쓰기가 가능하도록 구성한다.
> 파일 크기 5MB 제한은 (1) 클라이언트 선택 즉시 거부, (2) 스토리지 버킷 `file_size_limit`, (3) 이 테이블의 CHECK 제약, 3중으로 강제한다.
