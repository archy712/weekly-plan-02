# 부서별 주간업무일지 관리 웹 애플리케이션 MVP PRD

## 🎯 핵심 정보

**목적**: 부서원들이 한 곳에서 주간 업무 진행 상황을 기록·추적하고, 관리자는 모든 부서의 업무 현황을 한눈에 파악할 수 있게 한다.
**사용자**: 여러 부서로 구성된 조직의 실무자(부서 소속 일반 사용자)와 전체 부서 현황을 관리하는 관리자.
**범위**: 이 문서는 MVP(구현 완료, `docs/roadmap/ROADMAP_mvp.md` Task 001~024)와 v1 고도화(`docs/roadmap/ROADMAP_v1.md` Task 025~039)를 모두 포함한다. v1 중 관리자 콘솔(F019·F020)·기간 범위 검색(F021)·통계 대시보드(F024)·댓글·멘션(F022)·실시간 알림(F023)은 모두 구현 완료다. 원래 계획에 없던 업무 타입(다중 선택) 분류(F025)·업무 중요도(F026)·조직 계층 및 조직 관리(F027)·목록 Excel 다운로드(F028)·업무 타입 관리 UI(F029)·관리자 콘솔 조직 범위 제한(F030)·**슈퍼관리자 등급(F033)**·**슈퍼관리자 전 조직 범위 확장(F034)**·**목록 작성자 아바타 표시(F035)**도 Phase 3 이후 ad hoc 요청으로 추가되어 구현 완료됐다(`docs/ROADMAP_v1.md` "Phase 3 이후 ad hoc 확장" 참고). 여기에 사용자 요청으로 추가된 **주간업무일지 추천/비추천(F031)**은 결정 6종(자기 글 투표·노출 범위·익명성·통계 반영·인터랙션·관리자 예외)을 확정한 뒤 **구현 완료**됐고, **애플리케이션 전반 성능 개선(F032)**도 결정 항목을 확정한 뒤 **구현 완료**됐다(인증 계정이 필요한 E2E 회귀 검증만 사용자 작업으로 대기, `docs/ROADMAP_v1.md` Phase 6 및 "주요 리스크 및 결정 필요 사항" 표 참고). 이 문서는 구현 여부와 무관한 **목표 스펙**을 기술하며, 진행 상황은 로드맵의 체크박스로만 추적한다. v1 범위의 기능·페이지에는 **"(v1)"** 표기를 병기한다.

## 🚶 사용자 여정

```
1. 랜딩 페이지
   ├─ [로그인] 버튼 클릭 ──────────────┐
   └─ [회원가입] 버튼 클릭 ─────┐       │
                              ↓       ↓
                     2. 회원가입 페이지   2. 로그인 페이지
                     - 이메일/비밀번호     - 이메일/비밀번호 로그인
                       입력 후 가입         또는 [구글로 계속하기]
                     ↓ 가입 성공(이메일 확인 없이 즉시 로그인됨)
                     가입 완료 안내 표시(1.5초)   ↓ 로그인 성공
                     → 랜딩 페이지로 자동 이동 ────┘
                     (로그인 상태의 랜딩은 [주간업무일지 보러가기] 버튼 노출)
                              ↓
              3. 인증 상태 자동 확인 (부서 설정 여부 체크)

     [부서 미설정] → 4. 프로필 페이지(온보딩)         [부서 설정됨]
                     - 부서 선택 후 저장 ───────────────────┐
                     (저장 전까지 다른 페이지 접근 차단)       ↓
                                                  5. 주간업무일지 목록 페이지
                                                     (검색·부서 필터·페이지네이션, 모든 로그인 사용자가
                                                      전체 부서 조회 가능 — 기본값만 일반 유저는 자기 부서)
                     ↓ [신규 작성]        ↓ 항목 클릭         ↓ [PDF 다운로드]
              6. 작성 페이지         7. 상세 페이지          PDF 파일 다운로드
                 - 입력 후 저장        - 조회/수정/진행상태변경/삭제  (목록 페이지 유지)
                     ↓ 저장 성공          ↓ 완료
                     └──────── 5. 주간업무일지 목록 페이지로 복귀 ────────┘
```

- 부서 미설정 상태에서는 `주간업무일지 목록/작성/상세` 등 모든 보호된 페이지 접근이 자동으로 **프로필 페이지**로 리디렉션된다.
- 이메일/비밀번호 찾기 등 기존 스타터킷의 인증 보조 흐름(비밀번호 재설정 등)은 본 PRD 범위에서 변경하지 않고 그대로 유지한다.
- 회원가입은 이메일 인증(Confirm Email) 없이 가입과 동시에 로그인 처리된다(Supabase Auth 설정).
- 주간업무일지 **조회(SELECT)는 로그인한 모든 사용자에게 부서 무관하게 공개**되고, **쓰기(작성/수정/삭제/진행상태변경)만 작성자의 소속 부서 또는 관리자로 제한**된다. 상세 페이지는 서버에서 계산한 쓰기 권한(`canWrite`)에 따라 수정/삭제/진행상태 선택 UI 노출 여부를 결정한다.
- **(v1)** 관리자 계정은 공통 헤더의 "관리자 콘솔" 링크(관리자에게만 노출되는 유일한 진입점)를 통해 대시보드·조직 관리·부서 관리·업무타입 관리·사용자 관리 5개 탭으로 이동한다. 관리자가 아닌 계정은 URL을 직접 입력해도 주간업무일지 목록 페이지로 리디렉션된다.
- **(v1, ad hoc)** 관리자(`admin`)는 전부 **자기 소속 조직으로만 범위가 제한**된다(소속 부서가 속한 조직으로 자동 결정). **(v1, ad hoc)** `admin` 위에 **슈퍼관리자(`superadmin`)** 등급이 있으며(이미 `admin`인 사용자만 승격 가능, `user`에서 직접 승격은 불가), 슈퍼관리자는 조직(organizations) 생성·전 조직 범위의 수정/닫기가 가능하고 대시보드·부서 관리·업무타입 관리·사용자 관리 4개 탭도 전 조직 범위로 확장된다(F033·F034). 일반 관리자는 관리자 콘솔 5개 탭 전부 기존과 동일하게 자기 소속 조직 범위 안에서만 조회·관리가 가능하며, 조직 관리 탭도 여러 조직을 나열하는 목록이 아니라 자기 조직 1건짜리 카드(이름 수정·비활성화만 가능)로 남는다.
- **(v1)** 상세 페이지에서 댓글을 작성하며 `@`로 다른 사용자를 멘션할 수 있다(부서 무관하게 모든 로그인 사용자가 작성 가능). 자신이 멘션되거나 자신이 쓴 글에 댓글이 달리면 새로고침 없이 공통 헤더의 알림 벨에 즉시 표시되고, 클릭 시 해당 댓글 위치로 이동하며 읽음 처리된다.
- **(v1)** 관리자 콘솔의 대시보드 탭(관리자 전용, 관리자 콘솔 진입 시 기본 랜딩 화면)에서 부서별·기간별·상태별 업무 현황을 요약 카드와 차트로 확인할 수 있다.
- **(v1)** 상세 페이지에서 개별 주간업무일지에 추천/비추천을 남길 수 있다(댓글과 동일하게 부서 무관, **1인 1표**이며 같은 버튼 재클릭 시 해제·반대 버튼 클릭 시 전환). 자기 글에도 반응할 수 있고, 목록 페이지에도 익명 집계가 표시되며, 누가 눌렀는지 명단은 공개하지 않는다(F031).

### 3. v1 고도화 기능

> MVP에서 "MVP 이후 기능"으로 제외했던 6가지(F019~F024)를 정식 기능으로 명세하고, 이후 ad hoc 요청으로 추가된 F025~F030·F033~F035, 사용자 요청으로 구현 완료된 F031·F032까지 함께 기술한다. 상세 구현 계획(Phase·Task 단위)은 `docs/roadmap/ROADMAP_v1.md`를 참고. 관리자 콘솔(F019·F020)은 기존 `profiles`/`departments`의 RLS를 확장하는 유일한 작업군이라 다른 v1 기능보다 먼저 진행한다. **F031·F032는 한 줄짜리 구두 요청에서 출발**했다 — 둘 다 결정 항목을 확정한 뒤 구현 완료됐다(F032는 인증 계정이 필요한 E2E 회귀 검증만 사용자 작업으로 대기). 결정 항목의 목록과 확정 내용은 `docs/ROADMAP_v1.md`의 "주요 리스크 및 결정 필요 사항" 표에 정리되어 있다.

### 4. v1 이후에도 제외되는 기능

- 부서 계층 구조(상위/하위 부서), 부서장 지정, 부서 통폐합(로그 일괄 이관)

| 필드 | 설명 | 타입/관계 |
|------|------|----------|
| id | 고유 식별자 | UUID |

| created_at | 작성일시 | timestamp |
| updated_at | 수정일시 | timestamp |

> **(v1, ad hoc)** `organizations`는 관리자 콘솔(F027)에서 관리자 소속 조직 1건만 이름 수정/비활성화가 가능하다(생성·삭제 UI 없음). `UPDATE`는 `is_admin() AND id = current_organization_id()`로 제한된다. **(v1, ad hoc, F033)** 슈퍼관리자는 예외다 — 신규 `is_superadmin()` 함수를 조건으로 쓰는 별도 `INSERT` 정책(조직 생성)이 있고, `UPDATE` 정책도 슈퍼관리자에게는 `id = current_organization_id()` 조건 없이 전 조직에 열려 있다(`is_superadmin() OR (is_admin() AND id = current_organization_id())`).
> **(v1)** `departments`는 관리자 콘솔(F019)에서 추가/수정/비활성화(소프트 삭제)가 가능하며, `INSERT`/`UPDATE`/`DELETE`는 **`is_admin() AND organization_id = current_organization_id()`**(v1 ad hoc로 조직 조건 추가, F030) 조건의 admin 전용 RLS 정책으로 제한한다. 참조(부서원 또는 `weekly_logs`)가 있는 부서의 하드 삭제는 FK로 차단되므로 UI에서 소프트 삭제를 기본 동작으로 유도한다. **(v1, ad hoc, F034)** 이 조건에 `is_superadmin() OR` 분기가 추가되어 슈퍼관리자는 조직 조건 없이 전 조직의 부서를 쓸 수 있다(`work_types`의 동일 3개 정책도 같은 패턴).
> **(v1)** `profiles.role`은 관리자 콘솔(F020)에서 UI로 변경 가능하다. 단 `profiles`의 `UPDATE` 정책(`profiles_update_own_or_admin`)이 행 단위 제한만 하므로, `role` 값이 바뀌는 UPDATE는 호출자가 `is_admin()`이 아니면 예외를 발생시키는 `BEFORE UPDATE` 트리거로 별도 차단한다(일반 사용자의 자기 역할 상승 방지). 마지막 남은 관리자(`admin`∪`superadmin`)의 자기 강등도 동일한 트리거에서 거부한다. **(v1, ad hoc, F033)** 이 트리거에 승격 규칙도 추가됐다 — `superadmin`으로의 승격은 대상이 이미 `admin`인 경우만 허용(`user`→`superadmin` 직접 승격 거부). **(v1 ad hoc, F030)** `profiles`에는 조직 컬럼이 없어(부서를 통한 간접 소속) RLS로 조직 범위를 제한하기 어려우므로, 관리자 콘솔의 역할·소속 부서 변경 서버 액션이 대상 사용자와 새 부서가 호출자와 같은 조직인지 매번 재검증한다. **(v1, ad hoc, F034)** 이 서버 액션 검증은 슈퍼관리자에 한해 건너뛰어져 전 조직의 사용자·부서를 대상으로 변경할 수 있다.
> `weekly_logs`의 RLS는 SELECT를 전 부서에 공개하고, INSERT/UPDATE/DELETE만 작성자의 소속 부서 또는 `admin`(∪`superadmin`)으로 제한한다(이 SELECT 공개 범위는 관리자 콘솔 조직 범위 제한과 무관하게 유지됨). **(v1, ad hoc, F035)** 목록 페이지는 `author_id`로 작성자를 조회해 부서 배지 대신 아바타+이름을 표시하는데, `profiles_select_own_or_admin` RLS 때문에 PostgREST embed로는 타인의 이름·아바타를 가져올 수 없어 댓글 작성자 조회(F022)와 동일하게 `get_profile_identities` RPC로 배치 조회한다.
> `content`는 저장 시점과 렌더링 시점 양쪽에서 DOMPurify로 sanitize해 허용된 태그(`p, br, strong, em, u, h1~h3, ul, ol, li, a, blockquote`)만 남긴다(XSS 방어).
> **(v1, ad hoc)** `work_type`은 처음엔 코드에 고정된 10개 값만 허용하는 CHECK 제약이었으나, **관리자가 `work_types` 테이블(조직별 관리, F029)에서 직접 관리하는 방식으로 전환**됐다. CHECK 제약은 다른 테이블을 참조할 수 없어 `validate_weekly_log_work_type()` 트리거가 대신 "값이 1개 이상"과 "각 값이 작성 부서의 조직에 속한 `work_types.name`에 실존"을 검증한다. `work_types`의 `INSERT`/`UPDATE`/`DELETE` RLS도 `departments`와 동일하게 `is_admin() AND organization_id = current_organization_id()`로 제한된다(F030). 상세 페이지에서는 진행상태와 동일하게 별도 "수정" 모드 없이 체크박스에서 바로 체크/해제하면 즉시 저장된다.
> **(v1, ad hoc)** `importance`는 관리자 관리형이 아니라 코드 상수(`lib/constants/importance.ts`)로 고정된 1~5단계이며, DB CHECK 제약으로 검증한다. 상세 페이지에서는 업무 타입과 동일하게 별도 "수정" 모드 없이 슬라이더 조작만으로 즉시 저장된다.

| type | 알림 유형 | text (`mention` \| `comment` \| `reply` CHECK 제약) |
| weekly_log_id | 관련 주간업무일지 | → weekly_logs.id (on delete cascade) |
| comment_id | 관련 댓글 | → weekly_log_comments.id (on delete cascade), nullable |
| read_at | 읽음 처리 일시 | timestamp, nullable |
| created_at | 생성일시 | timestamp |

> 알림은 부서 기반이 아니라 **수신자 개인 기준**으로 RLS를 적용하는 유일한 테이블이다: SELECT는 `recipient_id = auth.uid()`만, UPDATE는 수신자 본인이 `read_at`만 변경 가능(다른 컬럼 변경은 트리거로 차단, `profiles.role` 보호와 동일한 패턴), DELETE는 수신자 본인만. **INSERT는 클라이언트에 허용하지 않고** `weekly_log_comments`/`weekly_log_comment_mentions`에 새 행이 생길 때 동작하는 `SECURITY DEFINER` 트리거로만 생성한다(자기 자신에게는 알림을 만들지 않음). Supabase Realtime publication에 이 테이블만 등록해 헤더 알림 벨(F023)에 실시간으로 반영한다.

### weekly_log_reactions (추천/비추천, v1)

> F031 결정 6종 확정 후 구현 완료(Task 038). 스키마·정책은 아래 확정본이다.

| 필드 | 설명 | 타입/관계 |
|------|------|----------|
| id | 고유 식별자 | UUID |
| weekly_log_id | 대상 주간업무일지 | → weekly_logs.id (on delete cascade) |
| user_id | 반응을 남긴 사용자 | → profiles.id (on delete cascade) |
| reaction | 반응 종류 | text (`up` \| `down` CHECK 제약) |
| created_at / updated_at | 생성/변경일시 | timestamp |

> `unique(weekly_log_id, user_id)`로 **1인 1표**를 DB 레벨에서 강제한다. 추천 상태에서 비추천을 누르면 행이 하나 더 생기는 게 아니라 기존 행의 `reaction`이 갱신되고, 같은 버튼을 다시 누르면 행이 삭제(해제)된다.
> RLS는 댓글(`weekly_log_comments`)과 동일하게 SELECT를 전 인증 사용자에게 공개하고, INSERT/UPDATE/DELETE는 `user_id = auth.uid()`인 **본인 행만** 허용한다. **부서 조건을 걸지 않는 두 번째 지점**으로, `weekly_logs`가 이미 전 부서 SELECT 공개이고 댓글 작성도 부서 무관인 상태에서 반응만 부서로 막으면 "타 부서 업무에 반응한다"는 기능 자체가 성립하지 않기 때문이다(F022와 동일한 근거).
> 집계는 `weekly_logs`에 카운터 컬럼을 비정규화하지 않고 이 테이블을 그때그때 집계한다(댓글수 표시와 동일한 방식). **확정된 결정**: 관리자 예외 **없음**(DELETE도 본인 행만) / 투표자 명단 **비공개**(익명 집계만) / 통계 대시보드 **반영**(`stats_reactions_summary` RPC, SECURITY INVOKER + `org_id` 파라미터, 0건도 up/down 2행 반환) / 자기 글 투표 **허용** / 목록에도 익명 집계 **노출**(댓글수 배지와 동일한 2차 조회) / 인터랙션 **낙관적 업데이트**.
